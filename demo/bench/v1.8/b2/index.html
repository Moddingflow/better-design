One call to send, one to check the seal

Your service hands the event to Relayhook and moves on. The receiving side verifies the signature before trusting the body.

Send from your app

import { Relayhook } from '@relayhook/node';
const relay = new Relayhook(process.env.RELAYHOOK_KEY);

await relay.events.send({
  endpoint: 'ep_billing',
  type: 'invoice.paid',
  payload: { invoice: 'in_1042' },
});

Receive on your endpoint

import { verify } from '@relayhook/node';

app.post('/webhooks/billing', (req, res) => {
  // throws on a bad signature or stale timestamp
  const event = verify(req.rawBody, req.headers, SECRET);
  handle(event);
  res.sendStatus(200);
});

Receive on your endpoint

from relayhook import verify

@app.post("/webhooks/billing")
def billing(request):
    # raises on a bad signature or stale timestamp
    event = verify(request.body, request.headers, SECRET)
    handle(event)
    return "", 200

Send from your app

relay := relayhook.New(os.Getenv("RELAYHOOK_KEY"))

_, err := relay.Events.Send(ctx, relayhook.Event{

Receive on your endpoint

func billing(w http.ResponseWriter, r *http.Request) {
  event, err := relayhook.Verify(r, secret)
  if err != nil {
    http.Error(w, "bad signature", 400)
    return
  }
  handle(event)
}

Retries on a schedule you set

Timeouts and 5xx responses go back in the queue. Every attempt carries the same event ID, so your handler can drop duplicates.

Example retry schedule for evt_7Hq2Lm

1at once503 Service Unavailable

Sealed before it leaves

Each request is signed with your endpoint's secret. Rotate the secret with an overlap window, and both old and new signatures verify during the switch.

Returned to sender, not lost

When the schedule runs out, the event lands in the dead-letter log with every response it got. Fix the endpoint, then replay one event or a whole range.

Questions

What counts as delivered?

A 2xx response within the endpoint's timeout. Redirects, 4xx and 5xx responses, and dropped connections are recorded as failed attempts.

Can the same event arrive twice?

Yes. Delivery is at least once: if your endpoint processed an event but the response was lost, Relayhook sends it again. Store the Relayhook-Event ID and skip IDs you have handled.

Does one slow endpoint hold up the others?

No. Each endpoint has its own queue, so a customer whose server is down does not delay deliveries to anyone else.

Do events arrive in order?

Not guaranteed once retries are involved. Each event carries the time it was created, so your handler can order updates or ignore stale ones.

Can my customers allow-list your IP addresses?

On Production and Dedicated, deliveries leave from a fixed set of addresses listed in the docs.
